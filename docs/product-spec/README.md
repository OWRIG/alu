# 产品行为账本

本目录借鉴 Keel 的“当前行为 + 修改申请 + 决策史 + 路线图”机制，但按单一桌面产品缩小范围。

## 四类文件

| 目录         | 回答的问题                   | 规则                                 |
| ------------ | ---------------------------- | ------------------------------------ |
| `specs/`     | 当前已实现、用户能观察到什么 | 只记录已验证行为                     |
| `changes/`   | 下一次准备改变什么           | 行为实现前先起草并由用户确认         |
| `memos/`     | 为什么这样设计               | 记录架构、调研和取舍，不冒充当前行为 |
| `roadmap.md` | 接下来做什么                 | 唯一的当前计划和开放问题索引         |

P1 alpha 已实现并逐 case 验证，当前行为见 `specs/`；验收历史保留在 `changes/2026-08-09-bootstrap-mvp.md`。P2–P4 仍是未批准草案，不属于当前产品能力。

## 标识符

- rule ID：小写点分，如 `project.portable-package`。
- case ID：`C-<语义名>`，如 `C-save-reopen-roundtrip`。
- ID 一旦使用就不得重新分配给别的行为。

每条规则至少有一个可判定 case。边界和错误场景按实际风险增加，不为凑格式虚构。

一个 changeset 对应一个可独立批准和验收的行为切片。后续阶段可以先建草案，但不得把 P1–P4 的 case 塞进同一张修改申请；当前 changeset 验收完成后，再批准下一阶段。

## 变更流程

1. 起草 changeset：写清现状、目标、不做什么和 case。
2. 用户确认行为契约。
3. 以 case 驱动实现和测试。
4. 对最终构建逐 case 验收并填写证据。
5. 同一次提交更新实现、changeset 验证记录和 `specs/` 当前行为。

changeset、当前行为和测试证据由同一次实现同步更新。仓库不使用只检查固定文件名的自动门禁；行为是否落地由 case 对应的领域测试、E2E 和当前行为文档共同证明。已交付的历史 changeset 不改名或挪作他用。

协议的目标是防止文档漂移，不是增加审批层。纯重构只需在提交中说明“不改变用户可观察行为”。
